# AGENTS.md

Instructions for AI coding agents (and humans) working in this repository. This file is model-agnostic: do not add tool-specific files such as `CLAUDE.md`; put shared guidance here.

## Project

Umpire: a framework and a rule engine that check the architecture of an app. Its first architecture pack is VSA (Vertical Slice Architecture). The repository has the base infrastructure, the scaffolding and the architecture rules, for use as the start of new projects. The reference apps are in the consumer repos (`docs/consumers.md`). Umpire is a working name.

The framework groups and their references are in `docs/framework-layout.md`.

There are three kinds of module: the VSA pack (`packs/Vsa/`), a plugin module and a feature module (the code of the app). A feature module is a folder `App/Features/<Feature>/`, and a plugin module is a folder `App/Plugins/<Plugin>/`. The code is in `Domain/`, `Domain/Shared/` (the published domain of the module), `Infrastructure/` and `Presenters/`. A feature module has its other code in `Slices/<Slice>/`. A plugin module has no slices: it has the layout of the framework, with one folder for each layer, for example `Handlers/Commands/`. Its module class inherits `Plugin` (`UMP020101`, `UMP020301`). The word "Shared" is only `Domain/Shared/` and `Slices/Shared/`. See `docs/slice-layout.md`. An app can also have its own packs in `App/Packs/<Name>/`: each one is an inner block with a kernel project (`Kernel/`) and a definition project (`Definition/`), and its architecture is its check entry. A pack variant there adds module kinds and rules to `VsaArchitecture`. See `docs/pack-variants.md`.

A VSA app has three roots in its block folder:

| Root | Folder | Contains |
|---|---|---|
| `App` | `App/` | `<Name>App.cs`, `Program.cs`, `Host/` (custom host code only), `Features/`, `Plugins/`, `Packs/`, `Tests/` |
| `Definition` | `Definition/` | Optional: the definition project with the architecture class, its records and externals, optional `Tests/` |
| `Views` | `Views/` | The views of a web app |

The project files and `.umpireconfig` stay at the top of the block folder. A pack has the same `Definition/` root, for example `packs/Vsa/Definition/Umpire.Vsa.csproj`.

An app has one root project in the block folder, for example `tests/Fixtures/Notes/Notes.csproj`. It compiles each file in its folder tree. All other projects are optional, for example a test project or a separate assembly. A parent project does not compile the folder of a nested project, and no project compiles `bin/`, `obj/` or the folders in `UmpireExcludedFolders` (default `node_modules`). The folders select the layers, and the rule engine checks each use. The name of a module is the last part of the namespace of its module class, and one assembly can have many modules. Each namespace starts with the app name and follows the folders under `App/`, for example `Notes.Features.Notebook.Slices.CreateNote`. Put the `using` directives inside the namespace, so a type of Umpire wins over a namespace of the app with the same name, for example `Host` or `App`. A file that names the block record `App` with no type arguments must put its `using` directives inside the namespace, else it gives CS0118. No namespace may be `Umpire.Core`, because the class `Umpire.Kernels.Core` then gives CS0118. This is a guideline, not an enforced rule. If the file is inside the namespace of the concept records (a pack variant), put some `using` directives outside the namespace. If that is not enough, add an alias inside the namespace. See "`using` placement" in `docs/architecture-engine.md`.

The block folder is the folder of the nearest check entry: the app class, the definition of a pack in its `Definition/` folder, a `Block<TArchitecture>` subclass, the `AssemblyMetadata` `Umpire.Architecture`, or the key `umpire.architecture` in a `.umpireconfig` file. For an app, it is the folder of the root project, also when `global.json` is in a folder above it. An outer definition marks the place of an inner block with `AddBlock<T>()` or `AddBlockGroup<T>()` (see "Blocks and check entries" in `docs/architecture-engine.md`). The kinds of block (app, pack, kernel, component, module, library), their entries and the composition guidelines are in `docs/blocks.md`. The framework knows no Unity layout. A host package (for example vsa-unity) gives its folders to the checks with the check settings in `.umpireconfig`: `umpire.check.folder_aliases` (for example `Assets/<AppName>/` binds as the block root, and the roots `App/`, `Definition/` and `Views/` are under it), `umpire.check.references` for its DLL folders, and `umpire.check.ignored_folders` (see "Folder aliases" and "Check settings" in `docs/architecture-engine.md`). The Unity build parts are in the `vsa-unity` package (MgCohen/vsa-unity#8). In this repository, `engine/`, `tests/Fixtures/` and the templates set the block folder (`UmpireBlock`) for each app, because the repository has one `global.json`. A plugin module is the base of the same layers in each module, as the framework is. See `docs/architecture-rules.md`.

The runtime and the definition code ship as bundle packages (`tools/bundle/`): `Umpire` (the core: one `Umpire.dll` with the markers, the config reader, the kernel and the messages, with no pack and no definition code), `Umpire.Vsa` (one `Umpire.Vsa.dll` with the VSA kernel: each layer base, `VsaKernel`, `Plugin` and the composition, with no views; its project is `Umpire.Vsa.Kernel.csproj`, because the source project of the VSA definition has the name `Umpire.Vsa`, and `Umpire.dll` gives its internals to it), `Umpire.Definition` (the definition API `Umpire.Architecture` with no markers, and `Umpire.Kernels.Definition`), `Umpire.Vsa.Definition` (the VSA definition `packs/Vsa/Definition/`), `Umpire.Web` (the web host and the views, with a dependency on `Umpire.Vsa`), `Umpire.Console` (the console host) and `Umpire.Testing` (the test bases, with a dependency on `Umpire.Vsa` and on the two definition packages). Each bundle compiles the source files of its runtime projects, so the runtime projects stay for development and enforce the layers with their references, and they are not packages (`UmpireBundled` in `Directory.Build.props`, `BundleSourceTests`). Each bundle embeds its PDB, with the source paths under `/_/`. Thus the rule engine binds each type of a kernel body in `Umpire.dll` and `Umpire.Vsa.dll` to that body by its PDB path (the core `Core`, `MessagesComponent` and the kernel root `Kernel` of the pack), and each other Umpire type to the External `UmpireLibraries` (assembly `Umpire`, which also covers `Umpire.Vsa`, `Umpire.Definition` and `Umpire.Vsa.Definition`). The engine reads the PDB path of a DLL type only if an `External` names its assembly. There is no Umpire SDK. A consumer project is a normal .NET project, `<Project Sdk="Microsoft.NET.Sdk">` or `<Project Sdk="Microsoft.NET.Sdk.Web">`, with a `PackageReference` to each Umpire package that it uses: a web root project references `Umpire.Web` and `Umpire.Engine` (`PrivateAssets="all"`), a module library or a pack kernel `Umpire.Vsa`, a definition project (a project in a folder `Definition/`, `UmpireDefinitionProject`) `Umpire.Vsa.Definition` (`PrivateAssets="all"`), a test project `Umpire.Testing`, `NUnit` and `NUnit3TestAdapter`, and a console app also `Umpire.Console`. Each dependency between the bundle packages has `PrivateAssets="none"`, so the build files and the analyzers flow through each package. The package `Umpire` brings the build files of each Umpire project in `build/` and `buildTransitive/`: `Umpire.props` (the block root, the definition project and the test project), and `Umpire.After.targets`, which the .NET SDK imports after its own targets (`AfterMicrosoftNETSdkTargets`): the source folders, the definitions, `.umpireconfig` as an additional file of the compiler and in the output folder, `Umpire.Codes.props`, the polyfills, the migrations and the architecture check after the build of the root project. The package `Umpire.Engine` holds the engine, and its `build/Umpire.Engine.props` sets `UmpireEngineFile` and `UmpireEngineDir`. With no `Umpire.Engine`, the root project gives `UMP030003`. The package of a pack names its definition for the check (`Umpire.Vsa`: `build/Umpire.Vsa.props`, the item `_UmpirePackDefinition`). Each project that is not a definition project and not a test project, and that has the engine, gives the definition of the pack only to the check: it copies the DLLs to its folder `umpire-definitions/` (in source mode from the build of `Umpire.Vsa`, in package mode from the engine folder `tools/net8.0/` of `Umpire.Engine`). The first restore of a project does not import the package files, so `Umpire.After.targets` restores the projects of the references that it adds (the target `_UmpireRestoreAddedReferences`). The package `Umpire` depends on the kernel analyzer package `Umpire.Kernels.Analyzers`, and the package `Umpire.Vsa` depends on the VSA analyzer package `Umpire.Vsa.Analyzers`. The analyzer package of the pack holds the kernel analyzer DLL too (pinned choice, `framework/Kernel/Analyzers/Umpire.KernelBundle.targets`), so in package mode the target `_UmpireOneKernelAnalyzer` of the package `Umpire` (`tools/bundle/Umpire/build/Umpire.targets`) removes the copy of `Umpire.Kernels.Analyzers` from a compilation that has the copy of a pack, and `KernelAnalyzer` runs one time. The kernel analyzer DLL embeds Umpire.Config, which it loads in a private load context (`Umpire.ConfigBundle.targets`, #233). The kernel of the app selects the pack (the app class, for example `App<VsaKernel, WebHost>`). A package only makes a pack available, and the analyzers of a pack run only in a compilation that selects that pack (`RuleAnalyzer.PackNamespace`, `PackSelection`, by the namespace of the pack, so they work on the bundle). Another pack is a normal `PackageReference`. A project that references only `Umpire` gets no VSA analyzer and no VSA definition. The kernel of a pack variant in `App/Packs/<Name>/` derives from `VsaKernel`, so it selects VSA. Give each Umpire package the same version. The rule engine checks each Umpire version (`UMP030401`). The packages do not set the output folder: the .NET SDK reads `UseArtifactsOutput` and `ArtifactsPath` before the package props, so `umpire new app` and `umpire init` write them in `Directory.Build.props` (see "Packages of an app" in `docs/consumers.md`).

Inside this repository, the engine, the fixtures and the templates use source mode: the `Directory.Build.props` of each block (and `tools/Files/Umpire.Files.csproj`) imports `tools/bundle/SourceMode/Umpire.SourceMode.props`. Their project files have the consumer form, with `Version="$(UmpireVersion)"` (the version check does not read a version with a property). Only a project file with a `PackageReference` to an Umpire package uses source mode (`UmpireSourceMode`). `Umpire.SourceMode.props` imports `tools/bundle/Umpire/build/Umpire.props` by path, and `Umpire.SourceMode.targets` changes each Umpire `PackageReference` to the project references of its source projects and analyzer projects, so the restore does not see it. `_UmpireUseBundle=true` (private) references the bundle projects in place of the runtime projects: the package `Umpire.Engine` builds its engine so.

All build output goes to `artifacts~/`, so no `bin/` or `obj/` folder is next to the code. Each block folder (`engine/`, each app in `tests/Fixtures/`, `tools/cli/Templates/`) has its own `artifacts~/`. The library projects and the test projects share `artifacts~/` in the repository root. Git ignores `Umpire.slnx`. To make it, run `dotnet run solution.cs`. The script adds each `.csproj` in the repository, except `tests/Fixtures/`. It keeps `tests/Fixtures/Notes/` and `tests/Fixtures/PackVariant/App/Packs/Ecs/Tests/`, because they are tests of a consumer. After you add, move or remove a project, run the script again. Do not edit `Umpire.slnx` by hand.

The app has one entry class, `MyApp : App<TKernel, THost>` (Umpire.Kernels, portable), in `App/<Name>App.cs`. It names its kernel and its host: Notes is `App<VsaKernel, WebHost>`, and the engine is `App<VsaKernel, ConsoleHost>`. The runtime names no definition. The definition names its kernel (`VsaArchitecture : Architecture<VsaKernel>`, by `VsaArchitecture<TKernel>`). The app class file imports `Umpire.Kernels`, `Umpire.Vsa.Composition` and the namespace of the host. The definition of an app with its own rules imports `Umpire.Vsa.Definition` (`VsaArchitecture`, the layer records, `Feature`, `Plugin` and `UmpireLibraries`), `Umpire.Architecture.Blocks` (the block kind records, for example `App` and `Kernel`) and `Umpire.Kernels.Blocks` (the records `Core`, `Module` and `Pack`). `Program.cs` is only `return new MyApp().Run(args);`. The app class has the lifecycle only: `Start`, `Run`, `Stop`, and the hooks `OnStart` and `OnStop`. Each `Start` makes a new host. `State` is `Stopped`, `Running` or `Stopping`. `Run` starts the app and waits until it stops. Code inside the app stops it with `AppStop.Request(exitCode)`. The stop runs on the app thread: the `SynchronizationContext` of `Start`, else the thread pool, or the thread of `Run`. `Stop()` on the app thread stops inline. A Unity shell calls `Start` and `Stop`. `Stop()` stops the app instance, and `Start` can then start it again. Custom root services go in a custom host: `MyHost : WebHost` overrides `Configure`, and the app class is `App<VsaKernel, MyHost>`. The rule engine finds the app class by the interface `IAppEntry<TKernel>` (`App<TKernel, THost>` implements it, and so can a launcher such as a Unity shell), and it reads the kernel from the metadata (`UMP030502` if the app has no app class). It finds the definition in this order: `<block>/Definition/`, a check entry of the block folder, the definition of the kernel. It never runs app code. An app and a definition that name different kernels give `UMP030507`, and an ignored definition of the block gives `UMP030511` or `UMP030512`. A definition of an inner folder that no build loads gives the warning `UMP030513`. See "Find the definition" in `docs/architecture-engine.md`. To add app rules, add the project `Definition/<Name>.Definition.csproj` with a `PackageReference` to `Umpire.Vsa.Definition` (a check-time DLL: the build of the app builds it first, with no reference to it), derive an architecture from `VsaArchitecture` there, override `Rules(RuleBook)` with no `base.Rules` call (the engine calls each level of the inheritance chain, `UMP010107`). The host finds the modules and the views by itself. To add a feature module, add its files under `App/Features/`. Do not edit `Program.cs`. Each module folder has exactly one module class at its top that inherits `Module` or `Module<TSettings>` (`Plugin` or `Plugin<TSettings>` in a plugin module), else startup fails (`UMP020301`). `Configure(IServiceCollection)` is `protected virtual`, so a module overrides it with `protected override`. A module class with no registrations is one line, for example `public sealed class PingModule : Module;`.

The host (`AppHost`, Umpire.Kernels) is the platform. It has `Build(args, app)` (compose only, with the `HostArguments` of `Arguments(args)`: the base host reads each `--Key=Value` and `--Key Value` argument, and `ConsoleHost` reads only the arguments from the first option), `Start(services, stop)` (the host work: the console operation, the web server, Ctrl+C and SIGTERM) and `Dispose()`, and it does not wait. `AppHost.Compose(services, arguments, kernel, types)` has a fixed order: `core.Install` (the class `Core`: `HostArguments`, `AppTypes`, `AppStop`, `[AutoRegister]`), then `kernel.Install` (it only calls `Kernel.Configure`), then the public `Module.Install(services, settings)` of each module in `Order` (it calls the protected `Configure(services)`, or for `Module<TSettings>` it gets the settings and calls `Configure(services, settings)`), then `Configure(services, types)` of the host, then the null logger if no logger exists (`DefaultLogging`: `NullLoggerFactory` and `ILogger<>`, with `TryAdd`). The core uses no `Microsoft.Extensions.Configuration` and no `Microsoft.Extensions.Logging`: only `Logging.Abstractions` and the dependency injection. `WebHost` gives `Arguments(args)` to the core and keeps the ASP.NET Core `IConfiguration` and logging for ASP.NET Core and the web modules. The app class names its kernel, so there is no kernel scan. `VsaKernel.Configure` installs each VSA layer by a direct call, and it registers one `Operation` for each request. `WebHost` (Umpire.Hosts.Web) maps each operation to an HTTP route and hosts the views. `ConsoleHost` (Umpire.Hosts.Console) runs one operation from the command line. `LocalHost` (Umpire.Kernels) is the transport of local method calls: its start does no host work, and after `Start` a caller sends a request with `app.Send(request)`. `Send` is an extension method only for an app with `LocalHost` (`THost : LocalHost`): `LocalHostApps` gives `OperationResult`, and `LocalRequests` (Umpire.Vsa.Composition) gives `Result<T>` for an `IRequest<T>`. The extensions reach the host through the `internal` member `App.RunningHost`, so the host stays private. `App.Services` is `protected internal`, and `IApp` has no `Services`: other code reaches the app through a transport, and the framework tests read it through `InternalsVisibleTo`. An app class can keep its host open (`MyApp<THost> : App<VsaKernel, THost>`), and each entry gives it, for example `new MyApp<LocalHost>()`. The rule engine refuses only an app class with an open kernel. No host knows VSA. A request can declare the static members `Group`, `Name` and `Effect` (defaults: the module name, the type name with no `Request` suffix, `Write`). The web route is `/api/{group}/{name}`, and the console words are `{group} {name}`. A host does not expose a command. `AppHost.ModuleProvider` (an `init` property, `IModuleProvider`) gives the modules: the default `ScannedModules` scans the app, `FixedModules` is a list by hand (for example in a test), and a host package can give its own provider that scopes the scan with `ModuleScan.In(assemblies)`. In the VSA rules, the app host may use the module class at the top of a module folder (`For<Host>().Uses<Module>(Depth.Self)`) and no other part of a module. A Unity app with its own container calls `host.Compose(services, arguments, kernel, types)` and builds the container itself. Module settings come from the ordered providers of `AppHost.Settings(types)` (`ISettingsProvider`). The first provider that answers wins, else the module gets `new TSettings()`. The default provider, `UmpireConfigSettings`, reads the table with the module name in `.umpireconfig`, for example `[Notebook]`. A module replaces a default with `services.Replace<TService, TImplementation>()`. A factory (`IFactory<T>`, `services.AddFactory`) makes objects that the container cannot make, for example Unity objects. `AppTypes` finds the modules in the loaded assemblies and the `.dll` files of the app. Each type scan (`Registered()`, `ConcreteTypesOf`, for example the presenters and the views root `ViewsRoot`) reads the assemblies of the modules and of the app class. `Build` makes one `AppTypes` instance (`new AppTypes(ModuleProvider, app.GetType().Assembly)`), and it reads each assembly one time. Other code gets its types from that instance, for example with `ConcreteTypesOf(typeof(TBase))`. The reflection uses are in `docs/composition.md`. Open generics: the container never closes a generic type. `CloseOpenDescriptors` in `AppHost.Compose` replaces each open module descriptor with closed descriptors, from the `[AutoClose]` types and a constructor walk, and an open `[AutoRegister]` class with no closed type stops the start. See "Open generics" in `docs/composition.md` (the repository source) and the guide https://claude.ai/artifact/5xxwYSBS2MNS3kupBP61rT (a private page). Module code registers services on `IServiceCollection` and resolves them with `IServiceProvider`. These interfaces are container-neutral, so do not add an Umpire container interface. To add a kind of registration, write a public `Add<Name>(this IServiceCollection services, AppTypes types)` extension in the project of its layer, and call it in `VsaKernel.Configure`. It finds its types with `types.Implementations(typeof(TBase))`. See `docs/composition.md`.

Each message goes through a pipeline to its handler (Umpire.Messages.Handlers). A handler takes `IEnvelope<TMessage>` and returns `Result<T>`. A handler of a base message type also handles each derived message (the nearest handler wins for a command or a request), and the message closes an open handler. Each send (`ICommandSender`, `IRequestSender`, `IIntegrationEventPublisher`) returns `Result<T>`. `Result`, `Error` and `Envelope` are in Umpire.Messages.Contracts, next to `IMessage`: domain code does not use them. A run is: early steps (a priority below 0), validators (priority 0), before steps, Before hooks, the handler, After hooks, after steps. Each After hook and each after step runs in each run, also after a reject or a throw, so a pair of steps with a low priority can hold a lock. Validators are found by type: each pipeline runs the validators of its validator bases (`.ValidatorsOf(typeof(TBase<>))`, default `Validator<>`, the presenter pipeline `PresenterValidator<>`). A `Validator<T>` is only in the slice of its handler. A hook (`BeforeCommandHook<T>`, `AfterCommandHook<T, TResult>`, `BeforeEventHook<T>`, `AfterEventHook<T>`) is in its own slice, and its name ends with `Hook` (`UMP020204`). No hook runs for a request. A step (`BeforeStep`, `AfterStep`, or the typed `BeforeStep<T>`, `AfterStep<T>`) belongs to one pipeline. A module defines a custom pipeline with `services.AddPipeline(new PipelineBuilder<TMessage>()...)`: handlers, hook bases (`HooksOf`), validator bases (`ValidatorsOf`), handler calls (`Calls`, or the short forms `CallsCommandHandlers`, `CallsRequestHandlers`, `CallsEventHandlers` and `CallsPresenters`), runner, steps with a priority, all by type, and `AfterHandled` with an action. `IHandler<T>` (Umpire.Messages.Contracts) is a marker: the pipeline calls each handler with a handler call (`HandlerCall<THandler, TMessage>`), for example `CommandHandlerCall<,>`, and the default pipeline of each kind adds its call. No handler interface has a default method. The handler bases select the pipeline of a message, and each kind adds its default pipeline the same way. Each message runs at once (`InlineRunner`), unless the pipeline names another runner. See `docs/handler-pipeline.md`.

A presenter shows the events of its own module: it inherits `Presenter` and implements `IIntegrationEventHandler<TEvent>`, and it gets each event of a live presenter scope, also when no view shows it. The event pipeline takes `IntegrationEventHandler<>`, and the presenter pipeline takes `Presenter` (`HandlersOf(typeof(Presenter))`) and raises `Changed` with `AfterHandled<Presenter>`. A view only renders: it inherits `PresenterWatcher` (one or more presenters) or `PresenterComponent<T>` (one presenter). A presenter does not publish events (`For<Presenters>().Denies<Contracts.Events.Publishing>()`, `UMP020101`). See `docs/presenter-events.md`.

## The rule engine

The rule engine checks the architecture of an app when it runs. It is a VSA console app in `engine/`: its host `ConsoleHost` sends its one request, `RunEngineRequest` (response `RunEngineResponse`, which implements `IExitCode`). Its `RequestHandler` is the composition root, one line for each step: Build (builds the root project, and each line of the build output becomes a finding), Changes (stops the check if no input changed since the last clean check, `UMP030201`), Blocks (finds the block of the project and its check entry, and checks the projects of the block, `UMP0303xx`), Versions (checks that the app and the engine have one Umpire version, `UMP030401`), LoadApp (creates the definition), Rules (checks the layer rules), then Report (sorts the findings and writes `file(line,col): error CODE: text` lines). The rules come from `architecture/Queries/` on plain data. Only the plugin `engine/App/Plugins/BuiltApp/Infrastructure/` reads the DLL and PDB files: `BinReader` reads the bin one time in the Blocks step (`MetadataLoadContext`, result `BinIndex`), `AppLoader` creates the one definition type, and ArchUnitNET reads the type facts for the rules. The engine definition (`engine/Definition/EngineArchitecture.cs`) gives ArchUnitNET only to `Infrastructure` (`rules.For<Infrastructure>().Uses<ArchUnitLibraries>()`). A step is a feature module with one command that inherits `EngineStep<TResult>` (plugin `engine/App/Plugins/Steps`). The Steps plugin also has the pipeline parts in `Infrastructure/`: the runner, the after step that records the findings, the step log and the run options (`RunOptions`). A pipeline step is in `Infrastructure/` of a module or of a plugin, and a `Validator<T>` is only in the slice of its handler. To add or remove a step, add or remove its line. Each step declares its stages (`IStepStage`: `Stage.Build` or `Stage.Check`). `--stage` selects the stages of a run, for example `--stage Check`, and with no `--stage` all stages run. Report runs in each run. The Steps pipeline collects the findings of each step. If a step throws, it records `UMP030001` and the run continues. If an earlier step fails, `Run` skips the step with an `if`, and `StepLog.Skip` records `UMP030002`. `--failfast true` stops the run at the first throw.

To add a step:

1. Add a feature module `engine/App/Features/<Step>/` with one slice.
2. Write the command: `public sealed record <Name>Command(...) : EngineStep<<Name>Result>, IStepGroup, IStepStage { public static int Group => <n>; public static Stage Stages => Stage.Check; }`. The group is the place of the step in `Run` (Build 1, Changes 2, Blocks 3, Versions 4, LoadApp 5, Rules 6, Report 7). The stages are the kinds of run that include the step. Its inputs are the results of earlier steps, for example `AppInput App`. If the step needs an earlier step that can fail, write `earlier.IsSuccess ? await commands.SendAsync(...) : log.Skip<<Name>Command, <Name>Result>()` in `Run` (`UMP030002`).
3. Write the result: `public sealed record <Name>Result(IReadOnlyList<Finding> Findings, ...) : IStepResult`. The Steps pipeline adds its findings to the report.
4. Write the handler: `CommandHandler<<Name>Command, <Name>Result>`. For an expected failure, return an `Error` with a code of the step: put each code in one `<Name>Codes` class, as `StepCode.Of<<Name>Command>(n)` (`UMP03` + group + case). Do not catch exceptions: the pipeline records them as `UMP030001`.
5. Add one line to `Run` in `RunEngineHandler`: `var x = await commands.SendAsync(new <Name>Command(...), ct);`.
6. Add a case to `tests/Engine.Tests`.

The package `Umpire.Engine` holds the engine (`tools/net8.0/umpire-engine.dll`, property `UmpireEngineFile`). The engine and its own projects target `net8.0` (`UmpireEngineLayer` in `Directory.Build.props`) with `RollForward` `Major`, so the same files run on the .NET 8 of a Unity 6000.6 Editor and on each newer runtime. Do not use an API that is new in .NET 9 or 10 in the engine or in a portable layer. The hook runs the engine with `--roll-forward LatestMajor` (`UmpireEngineRollForward`), because the engine loads the definition of the app, and a `net10.0` app does not load on .NET 8. After the build of the root project, `Umpire.After.targets` runs the engine with `--stage Check`, and the findings are build warnings (the default mode `Warn`). `umpire.check.mode = "Error"` in `.umpireconfig` makes them build errors. The root `Directory.Build.props` of this repository sets `UmpireCheckMode=Error`, and `engine/.umpireconfig` has the key. Each analyzer finding is a warning by default too: `WarningsAsErrors` in the root `Directory.Build.props` makes some codes errors in this repository. `tools/bundle/Umpire/build/Umpire.Codes.props` lists each Umpire code, so `TreatWarningsAsErrors` does not make it an error: add each new code there (a test fails if one is missing). `-p:UmpireCheck=false` stops the check for one build. `-p:UmpireCheckMode=Error` or `Warn` gives the mode of one build. In source mode (this repository), the hook runs the engine of the source build (`engine/artifacts~/bin/Engine/<config>/`). The engine checks itself with its own new output, and each other root project builds the engine first (a `ProjectReference` with no assembly). The fixtures set `UmpireCheck=false`, because some break the rules on purpose. A run also checks each used block: each inner block, and each block with a check entry in a DLL of a project reference (`deps.json` type `project`). Thus the build of `engine/` checks `engine/`, `packs/Vsa/`, `framework/Kernel/`, the Messages and Config components, `architecture/` and `engine/Versions/`. The framework blocks name their definitions (`framework/Kernel/Definition/`: folders only, no rules yet) with `AssemblyMetadata`. Each block has its own check stamp in `artifacts~/umpire-checks/` of the block: a run at any level skips a block that did not change since its last clean check (`UMP030202`). Delete that folder to check the block again. Run the engine with `dotnet engine/artifacts~/bin/Engine/debug/umpire-engine.dll --project <host project folder> --block <block folder> --bin <host output>`. It builds the project, then checks it, and its report has the build findings and the architecture findings.

## Core principles

- **Organize by slice, not by layer.** Each slice is one folder, `Slices/<Slice>/`, with its request, response, events, handler and helpers. A slice has one kind of handler: a request handler, an event handler or a command handler.
- **Slices are independent.** A slice uses only its own types and `Slices/Shared/`. An event is in the slice that publishes it.
- **Modules talk with commands and events.** A command goes to one handler of another module. Name the types `<Name>Command`, `<Name>Result` and `<Name>Handler`. See `docs/slice-layout.md`.
- **Keep shared code small.** Promote code to a shared location only when two or more slices genuinely need it.
- **Rules are enforced by tests.** Architecture rules live in `tests/` and must pass.

## Add a check

The levels, rules and base classes are in `docs/architecture-rules.md`. Use a library first: the built-in .NET analyzers, Roslyn, ArchUnitNET or NUnit. Tests use NUnit, so they also run in Unity.

1. If a built-in .NET rule does the check, set its severity in the root `.editorconfig`. This is the style of this repository only: the Umpire packages ship no native style, and a consumer sets its own.
2. If one file shows the problem, write a rule class on the group base of its DLL: `VsaRule` (group `02`) in `packs/Vsa/Tests/Analyzers/` for a VSA rule, `KernelRule` (group `01`) in `framework/Kernel/Analyzers/` for a rule about any code. The analyzer of that DLL (`VsaAnalyzer` or `KernelAnalyzer`, both on `RuleAnalyzer`) finds and runs it. The rule sets only its `Number` (the next free number of its group, never the number of a retired ID), its `Title` and its `Message`. The base makes the ID: `UMP01` + group + number. Each value that a rule uses (a limit, a list, an order) is an option: list it in `Options` with its default, for example `UmpireOption.Int(MaxKey, 120)`, and read it with `Values(...)`. A consumer changes a value in `.umpireconfig`. An option with no default and no value gives `UMP010001`, and so does a value that is not valid. A rule with a maximum inherits `LimitRule` and sets `DefaultMax`. A `KernelRule` is about any code (`IsModuleRule` is false), so it also checks the framework code. A `VsaRule` checks only modules.
3. Else change the rules of the VSA definition (`packs/Vsa/Definition/VsaArchitecture.cs`). Add a use rule (`Uses`, `Denies`), a count (`Has<T>()`, or `HasTypes<T>()` for the types that inherit a runtime type), a match (`Takes<T>()`), a trait (`Are<T>()`), a type place (`Type<T>().OnlyIn<S>()`) or a name (`NameEndsWith`, `NameStartsWith`, `NamedAfterGroup` in `Define`). The rule engine (`UMP020101`, `UMP020102`, `UMP020201`, `UMP020202`, `UMP020204`, `UMP020301` to `UMP020304`) checks them. A new kind of engine finding is a class on `ArchitectureRule` in `engine/App/Features/Rules/Slices/CheckRules/`, on the base of its group (`UseRule`, `PlaceRule`, `StatementRule`, `BlockPlaceRule`): it sets only its `Number`, and the engine runs it with no other change. See `docs/architecture-engine.md`.
4. Write a message that gives what is wrong, the type names, and the fix.
5. Add tests in `tests/Rules.Tests/`. For an analyzer, use the Roslyn analyzer test library (`AnalyzerTests.cs`). For the architecture engine, add a case to `tests/Architecture.Tests/` with the fixture apps in `tests/Fixtures/Architecture/`.
6. Add the rule to the table in `docs/architecture-rules.md`.

The bundles `Umpire`, `Umpire.Vsa`, `Umpire.Definition` and `Umpire.Vsa.Definition` and seventeen framework projects target only `netstandard2.0`, for Unity, for .NET apps, for the engine and for the compiler (one build: the engine loads the definition of an app, and a record of a `net8.0` build and of a `netstandard2.0` build have different methods, #301; the engine will run in the compiler as an analyzer, and an analyzer must target `netstandard2.0`): Umpire.Config, Umpire.Vsa.Domain, Umpire.Messages.Contracts, Umpire.Messages.Handlers, Umpire.Vsa.Contracts.Requests, Umpire.Vsa.Contracts.Events, Umpire.Vsa.Contracts.Commands, Umpire.Vsa.Handlers.Requests, Umpire.Vsa.Handlers.Events, Umpire.Vsa.Handlers.Commands, Umpire.Vsa.Presenters, Umpire.Vsa.Infrastructure, Umpire.Kernels, Umpire.Kernels.Definition, Umpire.Vsa.Composition, Umpire.Architecture and Umpire.Vsa (`UmpirePortableLayer` in `Directory.Build.props`). A module defines a request, a command, an event or a presenter one time, and the same code works on all hosts. Only the transports (Umpire.Hosts.Web, Umpire.Vsa.Views) need ASP.NET Core. The tests and the internal tools stay on `net10.0`. See "Runtime targets" in `docs/requirements.md`. The .NET-only DLLs and the engine get the 8.0 `Microsoft.Extensions` packages through `Umpire.dll`, unless they reference a newer version directly. ## Scaffolding: the umpire tool

The `umpire` tool (package `Umpire.Cli`) writes new apps, modules, plugin modules, packs, requests and commands. Each command, except `init` and `update`, writes only new files: it does not write over a file, it does not edit a file, and it stops if one of its files exists. The two exceptions change files: `umpire init` adds the missing setup to an existing app (one list of setup tasks in `tools/cli/Scaffolding/Setup/`, also used by `new app`), and `umpire update` changes only the Umpire versions. Each command is a class in `tools/cli/Commands/` that inherits one base in `Commands/Bases/` (`ToolCommand` or `AppCommand`). All add commands are one `AddCommand`, with one `AddKind` value for each kind. See "Add a command" in `docs/scaffolding.md`.

```bash
dotnet tool exec Umpire.Cli@<version> -y -- new app <Name>   # nuget.config, .gitignore, .umpireconfig, <Name>.slnx, AGENTS.md, <Name>.csproj (Microsoft.NET.Sdk.Web with Umpire.Web and Umpire.Engine), Directory.Build.props (the artifacts output), App/ (with Features/, Plugins/, Tests/), Views/
dotnet tool exec Umpire.Cli@<version> -y -- init             # an existing app: adds the missing setup, the artifacts output and the Umpire packages. --check true writes nothing
dotnet tool exec Umpire.Cli@<version> -y -- add module <Name>                     # the module class, the published domain key, a status request, a presenter, a page and a unit test
dotnet tool exec Umpire.Cli@<version> -y -- add request <Name> -m <Module>        # the request, the response and the handler
dotnet tool exec Umpire.Cli@<version> -y -- add command <Name> -m <Module>        # the command, the result and the handler
dotnet tool exec Umpire.Cli@<version> -y -- add plugin <Name>                     # a plugin module: its root and a base command in Contracts/Commands
dotnet tool exec Umpire.Cli@<version> -y -- add pack <Name>                       # a pack variant in App/Packs/<Name>: the kernel project and the definition project
dotnet tool exec Umpire.Cli@<version> -y -- test                                  # the tests of each *.Tests project of the app, with no test entry in global.json
dotnet tool exec Umpire.Cli@<version> -y -- doctor                                # the version check of the engine (UMP030401), with the tool version
dotnet tool exec Umpire.Cli@<version> -y -- update                                # the Umpire packages move to the version of the tool
```

The templates are in `tools/cli/Templates/`. They are one app that builds in `Umpire.slnx`, with the sample names `SampleApp`, `SampleModule`, `SampleAction`, `SampleChange`, `SamplePlugin` and `SamplePack`. The tool replaces these names. A template file with `SampleAction` in its path belongs to `add request`. A template file with `SampleChange` in its path belongs to `add command`. A template file with `SamplePlugin` in its path belongs to `add plugin`. A template file with `SamplePack` in its path belongs to `add pack`. Any other file under `App/Features/SampleModule/`, or with `SampleModule` in its file name, belongs to `add module`. All other files belong to `new app`. `tests/Cli` lists each template file with its command. If you change a template, build `Umpire.slnx` and run the tests in `tests/Cli`. See `docs/scaffolding.md`.
