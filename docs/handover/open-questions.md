## Check system topology (page "Check System Topology")

The proposals and the questions of https://claude.ai/artifact/GQkEAJ48rdzvsDjPtXfBgf. Each answer is in the words of the user.

### Answers

- **P1 (2026-11-25).** Accepted. "I want it to be unified. We only have one thing, the engine, period. If we have our own analyzers, they're inside the engine. There might be different entry points, but they all go through the same system."
- **P1, analyzers (2026-11-25).** Option A: all our analyzers are in the engine, also the generic rules. "Everything goes through the same place. They might have some extra utility. But every code that we have that checks, no matter what, goes through the same system. They get the config from the same place. We only have one point of maintenance." This changes K3: generic rules are engine operations that need no app model, not analyzers outside the engine.
- **P2 (2026-11-25).** One project, not two. "I'm fine with the separation in the internal folder structure, the internal code organization. It is decoupled, but we don't need two projects if it's not needed." Target `netstandard2.0`, if it works everywhere: only the TOML reader needed more, and we replace it. The analyzers do no I/O of their own: "They just trigger the engine, and the engine reads all the necessary files on its own. The only thing they might do is send the symbols." The flow: the engine has the saved state of all projects. At the start of a compilation, the analyzer sends the symbols of its project, and the engine updates that one entry. Then the analyzer checks type by type, and it updates each type fact when necessary, so the check is incremental.
- **P3 and Q1, terms (2026-11-25).** The levels: job, operation, rule. "A job is the whole thing, the operation is the second thing: an operation is checking architecture. One line of the architecture is one check or one rule." A job is one call of the engine: one input, one output. "We define jobs by using the standard VSA handler, very similar to what the engine had before. A job is one request, and the handler of that job calls several operations." An operation has its own logic: "if it needs to call checks or do the business logic that belongs to it, fine, that is scoped to the operation." Thus the K2 "jobs" (format, code check, architecture check, setup check, unit testing) are operations. The runner does not find jobs by type: each job handler names its operations, as `Run` does today.
- **Entry design (2026-11-26).** The analyzer triggers a job like any other caller of the app, with no knowledge of the container. The engine is host agnostic: `EngineApp<THost> : App<VsaKernel, THost>`, and each entry closes the host at definition (`EngineApp<ConsoleHost>` for the command line, `EngineApp<LocalHost>` for the analyzer). `AppHost` stays the base with no transport. `LocalHost` is the transport of local method calls: it exposes the requests as `app.Send(request)`, through an extension method that exists only for an app with `LocalHost`. The host stays private in `App`: the extension uses an `internal` member, nothing public. "I like the idea of exposing through an extension and not making it public, just internal." The runtime moves to `netstandard2.0` (the analyzer needs it), after a check of the APIs. Spike first: a one-request app in an analyzer, in `dotnet build` and in Visual Studio. Separate item: make `App.Services` internal or protected, after a check of its users.
- **P4 (2026-11-26).** Accepted with a change. Export is an operation. Report is not an operation: "Each operation can only fill the report. The job creates a report, the operations fill it, and the report goes back to whoever called the job. Whoever calls it does whatever it wants with it. So maybe we don't need specific job return types." Thus each job returns the same report type, and each caller (analyzer, console host, build) converts it.
- **P5 (2026-11-26).** Accepted "for now", with two plugins: Jobs (the pipeline parts of the jobs) and Facts (the data readers, `IFactSource<T>`). Outputs is not a plugin, because the callers convert the report (P4). Also: issue #380 (a handler returns `Task<T>`, and the pipeline makes the `Result<T>`).
- **P6 (2026-11-26).** Accepted for now. "We should strive for the minimal amount, but whatever is needed." `config.json` goes: the engine reads `.umpireconfig` with its own reader. The user is not sure that `block.json` is necessary. Still open: the source of the snapshot, and the facts of the DLL types (Q8).
- **P7, packages (2026-11-26).** Partly answered.
  - Targets: each package targets the lowest framework that its code needs. Do not keep a target from an old decision (for example the `net10.0` default). The engine, the runtime and the definitions target `netstandard2.0`. `Umpire.Web` needs ASP.NET Core, so `net8.0`. Result: `Umpire.Web` targets `net9.0`, because `Views.Map` calls `MapStaticAssets` (ASP.NET Core 9). `Umpire.Console` can be `netstandard2.0` if SIGTERM works with `AppDomain.ProcessExit`. Result: it stays `net8.0`, because on .NET 10 on Linux SIGTERM stops the process with exit code 143 and the runtime does not raise `ProcessExit`.
  - "The CLI is the same as web and console, it's just a host." The tooling (scaffolding) is a separate thing on its own layer, and the console host runs it.
  - The engine ships as one thing: "Just one thing. The minimum, the better." One package, `Umpire.Engine`, with the analyzer entry and the console entry.
  - The SDK goes. A consumer uses `Microsoft.NET.Sdk` and package references, and the packages bring their own `build/` props and targets. The output folder uses the standard .NET switch `UseArtifactsOutput` in `Directory.Build.props`: this repository keeps it, and a consumer can add it (`umpire init`). The engine state files use the intermediate output path, not `artifacts~/`.
  - `Umpire.Testing` (option A): one test package for consumers. It holds the unit test helpers (the test starts the app with `LocalHost` and sends requests) and a thin definition test base that calls the engine through `LocalHost`. No copy of the rules. This also answers Q7. The user: the design is for consumers too, for example a game that uses the engine to validate VSA and adds its own tests and rules.
- **Own checks of an app (2026-11-26).** Option A now: an app adds only rule lines, and a special case is a normal unit test. Later option C (a new rule line kind and its operation in a pack variant of the app), "potentially even B" (an operation class in the `Definition/` project of the app). K2 and #143 hold for now.
- **P8 (2026-11-26).** Option A: the shared code (config reader, `LoadedTypes`, `ClosedBase`, text file writer, version check) is a utility folder and namespace inside `Umpire`. No new package, DLL or source copy. Helpers that must not be public are `internal`, with `InternalsVisibleTo`.

- **Default interface methods (2026-11-26).** Accepted the design of draft PR #382 as the fix of the `netstandard2.0` blocker in phase 1: one handler call for each handler kind in the VSA pack, no `IRunnableHandler`, no `IPresenterHandler` (a presenter is a `Presenter` class that implements `IIntegrationEventHandler<T>`), `AfterHandled<Presenter>` raises `Changed`. - **The `umpire` tool (2026-11-27).** Option B: the tool is a VSA app with requests, handlers and modules in `tooling/`, and the build checks it as a block. `tools/` keeps only build scripts and packages.
- **Exit code after a stop signal (2026-11-27).** Option C: after Ctrl+C or SIGTERM, `umpire test` and `umpire check` give the exit code of their child process. `ConsoleHost` keeps exit code 0 for other apps.
- **App and host split (2026-11-26).** This replaces the host in the app type of "Entry design", and a part of "LocalHost channel". The app gets the host at the start: "the app being able to pass the host is fine." One way to start the app: "I hate having 2 entry points, run and start. You should have only one." No custom compositions: "The kernels install themselves, the core is fixed. The only variant would be the host that hopefully would be self sufficient." The app does not own the composition: "App is lifecycle, maybe - at most after this - also a interface with transport." The composition and the transport are two classes: "we can have a composition class that just installs, and then the app host be just the transport." The hosts use proper injection, not a lookup of services. `IRequest` becomes a basic type: "the idea is to turn iRequest something basic, which is fine." One operation flow for all transports: "console converting a argument into an operation, the local converting a request into operation, the API converting a payload into operation, but then it should have a standard operation flow." The spike is the draft PR #381.
- **Reversed host model (2026-11-27).** A proposal of the user, tested in the spike #381 (`spikes/host-reversed/`) and on the page https://claude.ai/artifact/F6jvJV9kdCe34Y2Jto2obD. Not decided yet. "make the host completely standalone, its the entry point of any comms", "composition goes from app -> composition -> rest", "host doesnt do any composition", "host potentially receives/wraps up, allowing even for multiple hosts at same time". The spike found faults in the lifecycle (a stop during the start is lost, a stop does not wait for running work). The open decisions are on the page.
- **Operations and the hub (2026-11-27).** An operation is only a way in. "Any host, any transport we have, be it local, API, whatever, has to have a conversion from their specific thing into operation. And the operation they build is minimal, is just some keys and values and dictionary." One type: "I would have imagined we only need one type, which would be our DTO." The mapping is built one time: "even if you use reflection, what not should be a one-time cost of creating a lookup or creating a factory at start time." The core owns it: "It should be a architecture agnostic element, outside -> core, creates operations. Its up to the architecture to decide how to handle it though." "Nothing becomes operation. The idea is to convert whatever type the architecture wants." The bus moves to the kernel: "we could potentially move the central message bus to kernel", and "any message, coming from operation or not, always goes to the central message hub first before finding the dedicated pipeline". The pipelines keep their levels: "add message specific handlers", "add type specific elements (steps/validators/hooks)", for example "add a handler to CreateNote", "add a validator to any featureHandler", "add a hook to any integration Event". Hub steps (app-wide): option A, the kernel and plugin modules only. A feature module adds steps only to its own pipeline.
- **Operation converter (2026-11-27).** The architecture registers one operation converter, and the core uses it before the hub: "require a operation converter... If there's no converter, we can just do a warning, and then after the converter it goes into generic bus." Without the architecture, the operation reaches nothing: "if it was not VSA... nothing would happen. But then others can do things differently." The spike (#381, `spikes/hub/`): no converter gives a warning at start and an error result for each operation, and two converters fail at start.
- **Views (2026-11-27).** A view scope is a concern of the architecture, not of the core: "The view scope for now is something architecture specific... We don't need this to be shared, we don't need this to be architecture level yet, because a lot of apps or architectures don't have views, right? Like consoles don't have views, so we can discuss later how to do views, but it's not a concern now. It's just the path towards it, like to be able to have that in architecture that matters." Thus the core keeps only the path open, and the VSA views (Blazor, Unity) wait. The spike (#381) found that a Blazor or Unity view cannot open a presenter scope when the host gets only the operations.
- **Start handle (2026-11-27).** Option B, with the name `AppInstance`: the one start method returns a handle that the caller can await and dispose (`Completion`, `Stop`, `DisposeAsync`, and `GetAwaiter`, so `return await app.Run(host);` stays one line). "I would call it app instance instead of app run, but I think B is interesting and that's a good idea to even move things to in the future." `app.Stop()` goes (option A): only `instance.Stop()` and the dispose of the instance stop a run.
- **Platform facts (2026-11-27).** Moved to issue #409, with the questions that go with it: "I have a feeling this goes together with the idea of providing custom configuration provider, custom module provider, deciding if the host wraps the app or the app wraps the host... is there a universe where we have the app already built and then we start different hosts and just pass the app to it?" Until then, the host gives the module provider and the settings, as in the current code.
- **Web routes and the web host (2026-11-27).** The web host maps one catch-all route for the operations, and filters come later: "I would go with whatever is simpler. So if maybe we can start with catch all and add filters later, better, instead of already creating technology that we don't want." The web host keeps its own composition for now, until the views are designed: "web host, it keeps its own composition for now. Whatever is easier for now as well."
- **First start form (2026-11-27).** Option A: `AppInstance Run(AppHost host)`, with the arguments in the host (`new ConsoleHost(args)`). One host for each run, and each host still composes, as today. `Run(params AppHost[] hosts)` and "the app composes" wait for issue #409.
